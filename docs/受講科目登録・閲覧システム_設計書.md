# 受講科目登録・閲覧システム 設計書（中身編）

> このドキュメントは「システムの中身（データ設計・API・ロジック・認証）」をまとめた設計メモです。
> 画面の見た目（UI）は ChatGPT 側で作成する前提のため、ここでは **画面から呼び出される裏側の仕様** を中心に記述します。
> 週間グリッド／全体図の具体的なレイアウトは、後日共有される既存画面の画像を反映して更新します。

- 作成日: 2026-07-02
- 対象: 大学研究室内で各学生の予定（受講科目）を確認するためのシステム

---

## 1. 目的・背景

研究室内で、各学生がどの時間に授業で埋まっているか／空いているかを共有・閲覧できるようにする。
ミーティングやゼミの日程調整の際に「誰がいつ空いているか」を把握しやすくすることが狙い。

### 主目的（設計の軸）
1. **時間割の共有・閲覧** … 各学生の受講状況を研究室内で見られる
2. **各自の空き時間の把握** … 週間グリッド上で埋まり具合／空きを確認できる

### コマ表示についての補足（ヒアリング結果）
- 現在の「全体図」（全員の予定を重ねたもの）には**科目名は表示されておらず**、各コマに **M1 / M2 / B4 / B3 などの学年ラベル**が書き込まれているだけ。

  → **科目名は登録する前提**とし、サマリ／詳細で表示を切り替える方針に更新（当初の「任意」から格上げ）。
  → データ上は `subject_name` を持ち、未入力でも動作するよう nullable のままにしておく（登録漏れ対策）。

## 2.2 ★最優先の改善要件

今回のリニューアルで**最優先**で解決したい既存の問題点。

### 改善1: 時間割グリッドの軸を転置する（縦＝時限／横＝曜日）
- **現状**: 行＝曜日、列＝時限（一般的な時間割感覚と逆）。
- **改善後**: **列＝曜日（月〜土）／行＝時限（1〜5限）** に転置する。
  - 一般的な大学の時間割・多くの人の感覚に合わせる。
  ```
  改善後のイメージ:
        月    火    水    木    金    土
   1限  ...   ...   ...   ...   ...   ...
   2限  ...   ...   ...   ...   ...   ...
   3限  ...
   4限
   5限
  ```
- **設計への影響**: データ構造（`day_of_week`, `period` を持つ）は転置に依存しないため、**描画の向きだけ変えれば対応可能**。API はコマ単位（day+period）で返し、フロント（ChatGPT作成）が「列=曜日／行=時限」で並べる。→ この向きを **フロント実装の必須仕様** として明記する。

### 改善2: クォーターをページ内で切り替えられるようにする
- **現状**: 1Q〜4Q が**それぞれ別リンク（別ページ）**になっており、切り替えるたびにタブを開き直す／戻る必要がある。
- **改善後**: **1画面のまま 1Q〜4Q を切り替えられる**ようにする。
  - UI 案: 学期ラベル部分を **タブ or ドロップダウン**にし、選ぶとページ遷移せずにグリッドだけ差し替わる（AJAX でデータ再取得、または4学期分を先読みして即切替）。
- **設計への影響**:
  - API は `GET /api/overview?quarter=:qid` のように**学期をパラメータで受ける**単一エンドポイントにする（学期ごとに別URLを作らない）。
  - フロントは学期切替時にこのAPIを叩いてグリッドを再描画するだけ（フルリロードしない）。
  - `GET /api/quarters` で全学期を返し、切替UIを動的に生成できるようにする。

> この2点（軸の転置・ページ内クォーター切替）を満たすことを最優先とする。

## 4. 認証設計（要確認ポイントあり）

### ★アクセス方針（決定）
- **閲覧はログイン不要**: サイトを開いてすぐ、誰でも全体の時間割確認画面・個人の時間割（スポット表示）を見られる。
- **編集時のみログインが必要**: 自分の時間割を登録・編集するときだけログインする。
- ログイン後は「本人の時間割のみ」編集可能（5章の権限モデルと整合）。
- 実装への影響:
  - 閲覧系API（overview / 個人schedule取得 / quarters）は**認証なしでアクセス可**。
  - 編集系API（schedule の PUT/POST/DELETE）は**認証必須＋本人チェック**。

### 既存システムの認証方式（コード確認により判明）
既存システムの実装を確認した結果、次の方式だった:
- **初回ログイン時はパスワード不要**（学番などで入れる）
- ログイン後に**本人がパスワードを設定**する
- 以降はそのパスワードで認証
- 保存先は**テキストファイル**で、氏名・パスワード・受講科目が**平文のまま**保存されていた

### ★決定: セルフサインアップ方式（管理者登録の破綻を修正）
当初は「管理者がメンバーを登録する」方式だったが、**空のDBでは最初の管理者すら作れない**（ブートストラップ問題）ため、**誰でもログイン画面から新規登録できる方式**に変更した（ユーザー決定）。

1. **新規登録**: ログイン画面の「新規登録」から、本人が学番・氏名・学年（or 教員）・パスワードを入力してアカウント作成。登録した瞬間からログイン状態になる
2. 以降のログインは学番＋パスワード
3. **管理者権限は設定ファイルで付与**: `src/config.php` の `ADMIN_STUDENT_NUMBERS` に列挙された学番のユーザーに、登録時・ログイン時に自動で管理者権限が付く（教員が変わったらリストを書き換えるだけ）
4. 管理者が画面からメンバーを追加する経路も残す（その場合はパスワード未設定で作られ、本人は**初回に学番のみでログイン→パスワード設定**という旧フローで入る）
5. **学期（クォーター）のブートストラップ**: 空のDBで起動すると、現在の年度の1Q〜4Qが自動作成される（4月始まりの年度計算で現在のQをアクティブに）

- 年度更新で新入生を追加したときも同じ流れ（新規メンバーは常にパスワード未設定で始まる）。
- **パスワードを忘れた場合は本人がログイン画面からセルフリセット**できる（学番を入力してリセット → 未設定状態に戻る → 学番のみでログインして再設定）。管理者によるリセットは設けない（ユーザー決定）。
  - 注: 学番を知っていれば誰でもリセットできるが、初回ログイン自体が学番のみで通る設計のため、リスク水準は変わらない（研究室内の信頼を前提とした設計として一貫）。
- **本人によるプロフィール管理**: ログイン後、本人が自分の学番・氏名・学年を変更できる（プロフィール画面）。パスワード変更は現在のパスワードの照合を要求する。

### ★保存方法だけは平文をやめてハッシュ化する（既存からの変更点）
フローは既存踏襲だが、**パスワードの平文保存だけは踏襲しない**。
- 既存のように平文でファイル保存すると、学生が大学ポータル等とパスワードを使い回している場合、ファイルを見られただけで**大学アカウントごと漏洩**するリスクがある。
- 本システムでは **DB（MySQL）にハッシュ化して保存**する（PHP標準の `password_hash()` / `password_verify()` で bcrypt ハッシュ。外部ライブラリ不要）。
- 使い勝手は一切変わらない（入力するパスワードも画面も同じ。保存形だけが変わる）。
- 受講科目・氏名はDB保存（テキストファイルは使わない）。

### セッション管理
- ログイン後は **PHP 標準のサーバセッション（`session_start()` + Cookie, HttpOnly, SameSite=Lax）** で状態管理。
- 小規模なのでサーバセッション + Cookie が実装がシンプルで安全（JWT は不使用）。

### ★方針: 認証は「後付け」でよい（開発順序の決定事項）
認証方式が未確定でも開発を止めないため、**認証は後から差し替えられる形にして、先に動くもの（登録・閲覧）を作る**。

- **認証を抽象化レイヤにする**: 「現在のログインユーザーを返す」処理を1箇所（例: `getCurrentUser()` / 認証ミドルウェア）に集約する。
  - 本体ロジック（時間割・全体図など）は「ログインユーザーが誰か」だけに依存し、**どう認証したかには依存しない**。
  - 認証方式を変えたくなっても、この1箇所を差し替えるだけで済む（本体を作り直さない）。
- **開発中の仮ログイン（スタブ）**: 学番を入れるだけで入れる簡易ログインで動作確認する（実装済み）。
- **本番前に本物へ差し替え**: 上で決定した「初回パスワード無し → 本人設定 → 以降は学番＋パスワード（ハッシュ保存）」方式を実装して切り替える。

> つまり開発順序は「①データ＋登録・閲覧を仮ログインで動かす → ②認証を本物に差し替える」でOK。

## 5. 権限（認可）モデル

| 操作 | 未ログイン（閲覧者） | 学生（本人） | 学生（他人） | 教員 |
|------|:---:|:---:|:---:|:---:|
| 全体図 閲覧 | ✅ | ✅ | ✅ | ✅ |
| 個人の時間割 閲覧（スポット表示） | ✅ | ✅ | ✅ | ✅ |
| 自分の時間割 編集 | ❌（要ログイン） | ✅ | ❌ | ✅（教員自身の分のみ） |
| 自分のプロフィール編集（学番・氏名・学年・PW） | ❌（要ログイン） | ✅ | ❌ | ✅（自身の分のみ） |
| 他人の時間割 編集 | ❌ | ❌ | ❌ | ❌ |
| 学期・ユーザー管理 | ❌ | ❌ | ❌ | ✅（管理者ロール） |

- 基本ルール: **閲覧はログイン不要（誰でも可）・編集はログイン必須かつ本人のみ**。
- **教員に他人を編集する権限は持たせない**（決定）。教員も「閲覧＋自分の分の編集」まで。
- 学期作成やユーザー管理などの運用操作のみ、別途 `admin` ロールで対応（教員 or 特定の管理担当者に付与）。
- ロールは `student` / `teacher`（＋運用操作用の `admin`）。

## 6. データモデル（ER 設計）

小規模のためテーブルは最小限。中核は「1ユーザー × 1学期 × 1コマ（曜日×時限）」を1レコードとする `schedule_entry`。

### 6.1 エンティティ一覧

#### users（利用者）
| カラム | 型 | 説明 |
|--------|----|----|
| id | PK | 内部ID |
| student_number | string, unique | 学番（ログインIDにも利用） |
| name | string | 氏名 |
| role | enum(`student`,`teacher`) | 役割 |
| grade | string, nullable | 学年（M1/M2/B4/B3 など）。教員は null |
| password_hash | string, nullable | パスワードのハッシュ（bcrypt）。**NULL＝未設定＝初回ログイン状態**（学番のみで入れる） |
| is_active | bool | 有効フラグ（通常は1。休学など一時的に非表示にしたい場合用。卒業者は残さず削除する） |
| created_at / updated_at | datetime | |

#### quarters（学期：クォーター）
| カラム | 型 | 説明 |
|--------|----|----|
| id | PK | |
| year | int | 年度（例: 2026） |
| quarter | int(1–4) | 第何クォーターか |
| label | string | 表示名（例: "2026年度 1Q"） |
| start_date / end_date | date, nullable | 期間（任意） |
| is_active | bool | 現在アクティブな学期か（初期表示に使用） |

- `(year, quarter)` で unique。

#### schedule_entries（受講コマ ＝ 埋まっているコマ）
| カラム | 型 | 説明 |
|--------|----|----|
| id | PK | |
| user_id | FK → users | 誰の |
| quarter_id | FK → quarters | どの学期の |
| day_of_week | int(1=月〜) | 曜日 |
| period | int(1〜) | 時限 |
| subject_name | string, nullable | 科目名。**詳細表示で使用**。登録推奨だが未入力でも可（nullable） |
| created_at / updated_at | datetime | |

- **unique 制約: `(user_id, quarter_id, day_of_week, period)`**（同じコマの二重登録を防ぐ）
- 「そのコマにレコードが存在する = 埋まっている / 存在しない = 空き」というシンプルな設計。

### 6.2 マスタ（設定値）
曜日・時限の定義はDBマスタ or 設定ファイルで保持。デフォルト案:
- 曜日: 月〜金（必要なら土も）。`day_of_week` = 1..5(6)
- 時限: 1〜5限（大学の設定に合わせる）。各時限の開始・終了時刻はマスタ or 定数。

（確定済み: 月〜土 × 1〜5限。2.1参照）

### 6.3 関連図（テキスト）
```
users (1) ──< (N) schedule_entries (N) >── (1) quarters
                     │
                     └─ 1レコード = 1コマ(曜日×時限)の「埋まり」
```

## 7. 主要ロジック

### 7.1 週間時間割の取得（個人）
- 入力: `user_id`, `quarter_id`
- `schedule_entries` から該当レコードを取得し、曜日×時限のグリッドに配置。
- レコードが無いコマ = 空き。

### 7.2 全体図（学年集計グリッド）
現在の運用（各コマに M1/M2/B4/Prof などの学年ラベルが並ぶ）を再現しつつ、**軸を転置（列＝曜日／行＝時限）**して描画する。
- 入力: `quarter_id`（＋任意で学年フィルタ）
- 処理:
  1. 対象学期の全 `schedule_entries` を取得。
  2. `(day_of_week, period)` ごとにグルーピング。
  3. 各コマに紐づくユーザーの `grade`（教員は `Prof`）を集計 → 学年ラベルの集合（例: `["M2","M2","M1","B3","B3"]`）を返す。
- 出力例（1コマ分）:
  ```json
  { "day": 1, "period": 1, "grades": ["M2", "M2", "M1", "B3", "B3"], "count": 5 }
  ```
- **描画の向き（★必須仕様）**: フロント（ChatGPT作成）はこの `cells` を **列＝曜日（月〜土）／行＝時限（1〜5限）** のグリッドに配置する（2.2 改善1 参照）。
- 学年ラベルは色分けする（2.1 の色対応表に従う）。
- 科目名を表示するオプションを付ける場合は、同APIで `subjects` も返せるようにしておく。

### 7.2.1 既存の表示機能（踏襲＝刷新後も必ず残す）
現行画面の以下4機能は、刷新後も**必ず維持**する。実装はフロント（ChatGPT作成）＋APIパラメータで対応。

#### (a) 学年フィルタ
- `B3/B4/M1/M2/教員` の表示 ON/OFF。
- 実装: API に `grades=B3,B4,M1` のように渡して絞り込むか、全件返してフロントで絞る（50人弱なら後者でも可）。

#### (b) ハイライト（空きコマの強調）
- ON にすると、**そのコマに誰もいない（`count == 0`）セルを黄色くハイライト**する。
- 学年フィルタと組み合わせる場合は「フィルタ後に誰もいないコマ」を空きとみなすか、全体で空きとみなすかを決める（既定: **表示中のメンバーで誰もいないコマ**を空き扱い）。
- 実装: フロント側で各セルの `count` を見て塗り分け。7.3 の共通空きコマ検索とロジックは共通。

#### (c) サマリ表示 / 詳細表示（表示粒度の切替）
- `サマリ`（既定）: 各コマに**学年ラベルのみ**（M2/M1/B4/B3/Prof）。
- `詳細`: 各コマに**氏名＋授業名**も表示。
- 実装: overview API に `mode=summary|detail` を持たせ、`detail` のときは各セルに人物情報（氏名・科目名）を含めて返す。
  ```json
  // mode=detail のセル例
  {
    "day": 1, "period": 1, "count": 2,
    "entries": [
      { "name": "山田太郎", "grade": "M2", "subject_name": "画像処理特論" },
      { "name": "佐藤花子", "grade": "B3", "subject_name": "実験A" }
    ]
  }
  ```
- **前提**: 詳細表示のために **氏名・科目名を登録しておく必要がある**（データモデルに反映済み。6章参照）。

#### (d) スポット表示（個人時間割のピックアップ）
- ドロップダウンから**個人名を選ぶと、その人1人の週間時間割を誰でも閲覧できる**。
- 実装: `GET /api/users/:id/schedule?quarter=:qid`（8章）を叩いて、選んだ人の時間割グリッドを表示するだけ。
- 閲覧は全員可（5章の権限モデルと整合）。

### 7.3 共通の空きコマ検索（日程調整）
- 入力: `quarter_id`, 対象ユーザー群 `user_ids[]`
- 処理:
  1. 全コマ（曜日×時限のマス目）を候補とする。
  2. 各コマについて、`user_ids` の中に `schedule_entries` を持つ人が1人でもいれば「埋まり」、誰もいなければ「全員空き」。
  3. 「全員空き」のコマ一覧を返す。
- 出力: 空きコマの `(day, period)` リスト（＋各コマで埋まっている人がいれば誰か、も返すと調整に便利）。

### 7.4 自分の時間割の編集
- コマ単位で登録／削除（トグル的な操作を想定）。
- 登録: `(user_id, quarter_id, day, period)` で upsert（unique制約で重複防止）。任意で `subject_name`。
- 削除: 該当レコードを delete。
- 認可: **ログイン必須かつ本人のみ**（他人の編集は不可、5章）。

### 7.5 ユーザー管理・年度更新（管理者機能）
年に1回、年度が変わったときに研究室メンバーを入れ替えるための機能。**管理者（教員 or 管理担当）のみ**が操作できる。

#### (a) ユーザー管理（随時）
- **メンバーの参加は原則セルフサインアップ**（本人がログイン画面から新規登録。4章）。管理者による追加は補助的な経路として残す。
- **追加（補助）**: 学番・氏名・学年・役割を入力して新規メンバーを登録する。この場合パスワード未設定で作られ、本人が初回に学番のみでログインして設定する。
- **編集**: 氏名・学年などの修正。
- **削除（完全削除）**: メンバーをシステムから削除する。
  - **物理削除**とし、**その人の受講コマデータ（全学期分）も連動して削除**する（DBの `ON DELETE CASCADE` で自動）。
  - 卒業生のデータはもう不要であり、残すとデータが重くなる一方のため（ユーザー決定）。
  - 削除は取り消せないため、**実行前に「本人のコマ○件も一緒に消えます」と確認ダイアログを出す**こと。

#### (b) 年度更新（年1回の一括処理）
年度替わりに管理者が行う操作を、1画面のウィザードでまとめて実行できるようにする。処理は次の2ステップ:

1. **卒業生の削除**: 卒業するメンバー（通常 M2 と、就職する B4）を選択して一括削除する（受講コマも連動して消える）。
2. **在校生の進級**: 残るメンバーの学年を一括で進める（B3→B4、B4→M1※進学者、M1→M2）。
   - 自動一括変換ではなく、**変換候補を画面に提示して管理者が確認・修正してから確定**する（B4は就職/進学で行き先が分かれるため）。

- **新入生の追加はウィザードに含めない**: 新入生は各自がログイン画面から新規登録する（セルフサインアップ、4章）。
- あわせて**新年度のクォーター（1Q〜4Q）を自動作成**し、新1Qをアクティブに切り替える。
- **削除は取り消せない**ため、実行前の確認画面で「削除される人数とコマ数」を明示してから適用する。進級は後から再修正できる。

#### 権限
- 上記はすべて `admin` ロール（5章）が必要。
- **admin の付与は `src/config.php` の `ADMIN_STUDENT_NUMBERS`（学番のリスト）で行う**。リストにある学番のユーザーは登録時・ログイン時に自動で admin になる。DBを直接触る必要はない。
- 一般ユーザーの画面には管理機能への入口を出さない（URLを直接叩かれても 403）。

    - 追加フォーム／行ごとの編集・削除ボタン
    - 削除時は「受講コマ○件も一緒に消えます。取り消せません」の確認ダイアログを必ず出す
  - **タブ2: 年度更新（年1回のウィザード、7.5(b)）**
    - Step1: 卒業するメンバーをチェックして削除（M2・就職B4を初期チェック状態で提示）
    - Step2: 在校生の進級プランを確認・修正（B3→B4 / M1→M2 は自動提案、B4は進学/就職を選択）
    - 確認画面 →「実行」で一括適用（新年度クォーターも自動作成）
    - ※新入生の追加ステップは無し（各自がログイン画面から新規登録するため）
- 使うAPI: `GET|POST|PATCH|DELETE /api/users`, `POST /api/admin/year-rollover`, `POST /api/quarters`

### 画面5: プロフィール画面（ログイン後・本人のみ）
- ヘッダーの自分の名前（👤）をクリックして開く。
- 内容:
  - **基本情報の編集**: 学番（＝ログインID）・氏名・学年（教員は学年欄なし）
  - **パスワード変更**: 現在のパスワード＋新しいパスワード×2（照合あり）
  - すべてのパスワード欄に目マーク（表示切替）
- 編集できるのは本人の情報のみ（`PATCH /api/users/:id` の本人権限）。
- 使うAPI: `PATCH /api/users/:id`, `POST /api/auth/set-password`, `GET /api/auth/me`
